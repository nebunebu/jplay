# Suggestions

Design questions raised while writing `SPEC.md`, and how each was decided.
The spec is authoritative; this file records the reasoning.

## Settled

### Sample-data corrections (`6789.json`)

The original hand-written `6789.json` fixture predated the finalised schema
(`face_value` instead of `value`, inconsistent `wager` keys, Daily Doubles
whose `value` held the wager). **Resolved:** that fixture is retired. The
canonical example is now `jarch/testdata/6789.golden.json`, generated by the
parser from the cached page, so it conforms to the schema by construction:
every clue has `value` and `wager`, and DD `value`s are derived from row
siblings.

### `host_comment` / `post_response_comment`

Both a remark about the clue and a remark adjudicating a response render as an
identical `(Host: …)` parenthetical in the same position, so the split is not
machine-determinable. **Decision:** keep both fields; the parser puts every
host parenthetical in `host_comment` (joined with newlines) and always emits
`post_response_comment: null`, reserving it for a manual/curated pass.

### Response list source

Early parsing turned every contestant parenthetical into a response, scoring
mid-clue banter (e.g. a quip on a triple stumper) as a wrong answer.
**Decision:** the right/wrong `<td>` rulings are authoritative; a
contestant's last parenthetical is attached as `given_response`.

### Nickname ↔ full-name mapping

Clue and score data use short nicknames (`Carolyn`); `contestants[].name`
holds full names. Consumers previously guessed by first name, which fails for
`Matt`/`Matthew` or two contestants sharing a first name. **Resolved:** each
contestant now carries `nickname` (see SPEC "contestants" for the assignment
rules), and jplay's loader joins on it, falling back to the first name only
for JSON produced before the field existed.

### Tournament round vocabulary

**Resolved:** tournament-shaped notes with no recognised round keyword produce
a warning on stderr (`jarch: no round keyword recognised in note: …`), so the
keyword list can be grown from real misses. Extend `roundRE` in
`jarch/common.go` as they appear.

### Empty / unrevealed clues

**Decision:** cells with no clue are omitted from `clues`; a present but
unplayed clue has `play_order: null` and `responses: []`. Consumers must not
assume 30 clues per round.

### `combined_coryat` placement

**Decision:** stays flat at the top level next to `coryat_scores`, matching
existing output and jplay's loader. Nesting (`"coryat": {per_contestant,
combined}`) was considered and rejected as churn without a consumer need.

### `scores` shape: object vs array

**Decision:** round `scores` stays an object keyed by snapshot
(`after_clue_<N>`, `end_of_round`), with keys in page order. An array of
labelled snapshots would be more uniform to iterate, but nothing consumes it
in a way that needs that today.

### `href` absolute-URL alternative

**Decision:** hrefs stay site-relative; they double as cache filenames.
Resolve against `jarch.BaseURL` when an absolute URL is needed.

### `score_remarks` under "Final scores"

**Decision:** not captured. Revisit (as an optional `remarks` on the `final`
snapshot) if a page with meaningful content there turns up.

## Open

- **Season/episode identifiers.** Season ids are opaque strings (`42`, `pcj`)
  and episode numbers restart within tournaments, so "episode 49" is
  ambiguous without its season; the only global key is `game_id`. A future
  `jplay --fetch` convenience could accept a season title or an
  `<season>/<episode>` pair and resolve it to a `game_id` via the season page.
